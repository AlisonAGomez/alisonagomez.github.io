Resumo

Revisão manual de aplicação web e API

Foram realizados testes autorizados com Burp Suite Community Edition para mapear rotas, observar chamadas de API e validar o comportamento de autenticação em endpoints administrativos.

Resultado objetivo

No endpoint testado, a autenticação Bearer funcionou como esperado: sem o cabeçalho de autorização, a API respondeu com acesso negado. Nenhum bypass de autenticação foi demonstrado.

Metodologia

Testes pequenos, reproduzíveis e comparáveis

  1. 01 · MapeamentoNavegação pelo proxy para identificar rotas e chamadas de API.
  2. 02 · Requisição de controleCaptura de uma chamada válida para comparação.
  3. 03 · Variação de headersRemoção controlada de headers de navegador para verificar dependências inadequadas.
  4. 04 · AutenticaçãoComparação da resposta com e sem o cabeçalho de autorização.
  5. 05 · RegistroDocumentação do que foi confirmado, do que não foi confirmado e do que permaneceu pendente.
Constatações

Comportamento observado sem extrapolar a evidência

  • Rotas inexistentes do frontend retornavam a página principal da SPA, comportamento informativo para roteamento e observabilidade.
  • Headers como Referer, User-Agent e Sec-Fetch não atuavam como controle de segurança, o que é esperado.
  • A API exigiu autenticação no endpoint avaliado.
  • Testes de autorização entre organizações permaneceram fora da conclusão porque exigiam condições adicionais de homologação.
Valor técnico

Separar comportamento estranho de vulnerabilidade real

O principal aprendizado do trabalho foi manter uma classificação baseada em evidência: um HTTP 200, um fallback de SPA ou a remoção de um header não foram tratados como vulnerabilidade sem impacto demonstrado.

Privacidade e limites

Sem dados do ambiente analisado

O portfólio não publica hostname, domínio interno, tokens, identificadores de organização, dados de clientes, requisições completas ou outros elementos do ambiente corporativo.
